# icloud-relay-lookup — アーキテクチャ

この文書は設計の「なぜ」を記録する。「何をするか」は
[AGENTS.md](../../AGENTS.md) と各パッケージの doc コメントを参照。

## 問題の形

Apple は iCloud Private Relay の出口レンジ全体を単一の公開 CSV（約28.7万行、
約12MB）として配信している: CIDR prefix + その出口が受け持つ地域のジオヒント
（国 / ISO 地域 / 都市）。我々が答える問い —「この IP は Private Relay の
出口か？」— はこのリストへの longest-prefix match であり、ヒット時には Apple
自身のジオヒントをそのまま返す。

設計を決めた3つの性質:

1. **リストはそこそこ大きいが変化は緩やか**で、Apple は `ETag` と
   `cache-control: max-age=3600` を付けて配信している。よって: 積極的に
   キャッシュし、安価に再検証し、ルックアップごとのフェッチは決してしない。
2. **フォーマットは非公式・無バージョン。** Apple は URL を文書化しているが
   スキーマは文書化しておらず、列構成は予告なく変わり得る。よって: 寛容な
   パース + 明示的なフォーマット変化ガード。ゴミを黙って索引化しない。
3. **システムのどこにも認証情報が存在しない。** tor-exit-lookup と同じく
   エンドポイントは公開されており、設定は構造的に秘密を持たない。

## なぜオフラインストアか、なぜ生 CSV + meta.json か

姉妹品 asn-lookup / tor-exit-lookup と同様、一度ダウンロードしてローカルで
答える: IR やログトリアージは数百件のルックアップをバーストで撃つのであり、
ルックアップごとのネットワーク往復（やレート制限）はこのツール群がまさに
避けるために作られたものだ。

tor-exit-lookup は数千アドレスをソート済み JSON ストアに再シリアライズする。
本ツールで同じことをすると約29万行を利益なしに書き直すことになる:
ダウンロードした CSV はそれ自体が決定論的なバイト列で、既にコンパクトで、
既に正本である。よってストアは **CSV そのまま** + CSV が持てないものを運ぶ
小さな `meta.json`（`fetched_at`、`etag`、ソース URL、件数）とした。鮮度は
ファイル mtime ではなくレコード内に持つ — コピーやバックアップでも保たれる、
姉妹品と同じルール。

この分離は 304 経路も自然にする: `Not Modified` の再検証は `meta.json` だけを
書き直し（`fetched_at` を更新）、12MB の CSV には触れない。系として、パース
済みリストをキャッシュする側は `meta.json` の mtime をキーにしなければ
ならない（MCP サーバーはそうしている）。

約28.7万行のロード時パースは100ms のオーダー — CLI 起動には無視でき、常駐の
MCP サーバーでは償却されてゼロになる。

## なぜ prefix 長ごとのマップか（trie でもソート済みレンジでもなく）

longest-prefix match の定番は radix trie か、ソート済み非重複レンジへの
二分探索だ。どちらも同じ理由で退けた: データの規模に対してコードが過剰で、
ソート済みレンジ方式は prefix が重複しないときにだけ正しい — 今日のリストが
たまたま持つ性質に依存したくない。

決め手となる観察: 実リストは **約19種の prefix 長**しか使わない（v4 は
/24〜/32、v6 は /40〜/64）。長さごとに1つのハッシュマップを持ち、クエリ
アドレスをその長さでマスクして引けば、1回のルックアップは最大でも長さの
数だけのマップ参照で済む — 長い方から照合するのでより具体的なレンジが勝ち、
重複は構造的に処理される。数十行で、明らかに正しく、索引構築（ルックアップ
ではなく）が支配項になる程度に速い。

メモリ: `netip.Addr` → int32 の約29万エントリで数十MB。CLI にも常駐 MCP
サーバーにも問題ない。

## なぜフォーマット変化ガードはハードエラーか

`relaylist.Parse` は行単位では寛容（不正行はカウントするだけで致命傷に
しない）— これで表面的な揺れは吸収する。しかし**非空行の10%超**がパース
できない場合、`engine.Update` はダウンロードを拒否し（`ErrFormatChange`）、
直前のキャッシュを維持する。代替案 — たまたまパースできたサブセットを受け
入れる — は「出口である」を「ファイルのうち我々がまだ理解できた部分に
載っていた」に静かにすり替える。正しい答えの皮を被った誤答だ。完全だが
古いリスト + 大きな警告は、新しいが欠けたリストに勝る。

空ボディも同じルールに落ちる（0行中0行パース ⇒ 拒否）。上流が空の 200 を
返し始めてもキャッシュは消えない。

## 鮮度: TTL フロア、StaleAfter、graceful degradation

2つの時計を意図的に分けている（tor-exit-lookup と同じ方式）:

- **TTL（デフォルト1時間、フロア1時間）**は `check` の自動再検証を駆動する。
  フロアは Apple 自身の `max-age=3600` に合わせた — それより速いポーリングは
  何も買わないし、条件付き GET のおかげで毎時の再検証はほぼ無料だ。
- **StaleAfter（7日）**は `status` / `cache_status` の警告を駆動する。出口
  レンジの変化は分単位ではなく週単位のオーダー（上流が30分ごとに更新される
  tor-exit-lookup の24時間と対照的）なので、「まだ有用」が「警告に値する」に
  変わるのは1週間とした。

`EnsureFresh` は失敗ではなく劣化を選ぶ: 再検証がエラーになってもキャッシュが
あれば、呼び出し側は古いリスト**と**エラーの両方を受け取り、stderr に警告を
出してそれでも答える。「キャッシュがなく、かつフェッチも失敗」だけが致命傷。
不安定なネットワーク上の午前3時の IR ワークフローが受け取るべきは、警告付きの
少し古い答えであって、拒否ではない。

## 姉妹品と共通の不変条件

tor-exit-lookup / asn-lookup の系譜から、同じ理由で引き継いだもの:

- **1つのエンジン、2つのフロントエンド。** CLI と MCP は同じ `engine.Engine`
  を駆動するので、答えが食い違えない。
- **注入されるクロックとフェッチャー。** 非決定性は `engine.Now` と
  `apple.Fetcher` だけ。テストは密閉・オフラインで走る。
- **アトミックなストア書き込み**（temp + rename）: 更新中のクラッシュが
  切り詰められた CSV や meta.json を残すことはない。
- **grep 流終了コード**（単一 IP テキストモード: 0 出口 / 1 非出口 / 2
  エラー）。バッチモードの終了コードはエラー有無専用。
- **usage.md はテストで固定**: MCP マニュアルは `usage_test.go` を割らずに
  公開ツール群から乖離できない。
- **標準ライブラリのみ。** このツールの仕事は HTTP GET 1回、CSV パース1回、
  ハッシュルックアップ1回。依存ツリーは得るものより失うものが大きい。

## このツールが意図的に知らないこと

リストが対応付けるのは出口レンジと提供対象地域である。したがってヒットの
意味は「この接続は Apple のリレーインフラの、およそこの地域向けの出口から
出てきた」であり、ユーザーの特定や位置追跡では**ない**（それを防ぐことこそ
Private Relay の目的だ）。ミスも「Apple ユーザーではない」を意味しない。
ツールはシグナルをジオヒント付きで報告し、解釈はアナリストに委ねる — MCP の
usage マニュアルはエージェント利用者向けにもこれを明記している。

逆引き列挙（国 → 全レンジ）は検討の上で切った: IR の核心の問いは IP 単位で
あり、結果セットは巨大で、追加すればこのツールが避けている workspace /
ファイル媒介の機構を引き込むことになる。RFP の Discussion Log を参照。
